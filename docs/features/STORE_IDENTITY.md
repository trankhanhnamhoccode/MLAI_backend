# Store and identity persistence — S1.1

## Status

CURRENT FACT: User, Store and StoreMembership models/schema implemented. Scope is
persistence only. **No public Store/User/Membership API exists yet.** Repositories,
application services, authentication and authorization enforcement are NOT IMPLEMENTED.
S1.2 catalog/recipe persistence is documented separately in CATALOG_RECIPE. Slice acceptance evidence is in CURRENT_STATE.

## Purpose, entities and relevant ADRs

User stores a human identity; Store stores the F&B business context;
StoreMembership links User ↔ Store for future authorization. Storage semantics are
accepted in [DATABASE_SCHEMA](../DATABASE_SCHEMA.md), under ADR-002 (modular boundaries)
and ADR-007 (PostgreSQL, synchronous Session, Alembic, isolated test database).
ADR-006 future simulation/mutation permission distinctions remain future behavior.

## Business/storage invariants

- UUID PKs generated by PostgreSQL; explicit IDs allowed. Required fields NOT NULL.
- Email unique, nonempty, lowercase according to PostgreSQL `lower()`, no whitespace.
  Noncanonical values are rejected, not rewritten. No login/verification or full
  email validation. password_hash is opaque/nonblank storage, no hashing algorithm.
- Store names nonblank but not unique. Default timezone Asia/Ho_Chi_Minh, currency
  VND; currency accepts uppercase three-letter shape, no ISO catalog/financial rules.
- At most one membership per store/user; both UUID references must exist.
  Role exactly OWNER/STAFF. Deletion of referenced parents is restricted.
- delegated_permissions must be JSONB `[]`; no permission vocabulary is introduced.
- TIMESTAMPTZ insertion defaults `now()`; engine sessions UTC. ORM updates advance
  updated_at; raw SQL updates must set it explicitly. No timestamp triggers.
- active defaults true but has no enforcement semantics yet.

## Tables read/written and persistence behavior

Direct Session persistence uses `users`, `stores`, `store_memberships` only.
Migration `0002_identity_store` creates them after `0001_scaffold`, and writes the
Alembic revision. Status/seed read state in a fresh read-only transaction. Seed
creates no identities or other entities. Every normal reset leaves all three empty.
All persistence is current mutable state; no snapshot or audit-history behavior.

## Automated tests and fixtures

`tests/integration/test_identity_store_schema.py` uses only shelfcash_test:
exact migration tables, PK/FK/unique/index/NOT NULL/type/default inspection, model
metadata agreement, User/Store/Membership commit-close-reload, canonical-email,
pair/role/FK/permission/currency rejections, parent deletion restriction, UUID raw
SQL defaults and aware UTC/update timestamps. Existing bootstrap tests cover
downgrade through the original baseline and upgrade back to the new head.
Tests create isolated fixed records and dispose connections before reset; no real
credentials/provider/hosted notebook needed. Password values in tests are opaque
test placeholders, not an authentication example. No canonical demo seed is added.

## Manual verification procedure

From backend/ with Docker running; stop backend/DB clients before reset:

```powershell
docker compose up -d postgres
docker compose up -d --wait --wait-timeout 90 postgres
.\scripts\reset_db.ps1
.\.venv\Scripts\alembic.exe upgrade head
.\.venv\Scripts\alembic.exe current
.\.venv\Scripts\python.exe -m pytest tests/integration/test_identity_store_schema.py -q
.\scripts\test.ps1 all
.\scripts\db_status.ps1
```

Expected: healthy PostgreSQL, revision `0005_data_semantics_correction (head)`, targeted/full
tests pass, development status reachable/at_head true, tables/row counts exactly
`alembic_version: 1`, `users: 0`, `stores: 0`, `store_memberships: 0`,
`products: 0`, `ingredients: 0`, `recipes: 0`, `recipe_lines: 0`,
`suppliers: 0`, `supplier_terms: 0`, `sales_daily: 0`, `inventory_lots: 0`,
`inventory_movements: 0`, `business_constraints: 0`.
Tests write only shelfcash_test, so development tables remain empty after testing.

Inspect columns/defaults and named constraints without a GUI or host psql:

```powershell
.\.venv\Scripts\python.exe -c "from app.config import Settings; from app.infrastructure.database.engine import create_database_engine; from sqlalchemy import text; e=create_database_engine(Settings()); c=e.connect(); print(c.execute(text('SELECT table_name, column_name, data_type, is_nullable, column_default FROM information_schema.columns WHERE table_schema = :schema ORDER BY table_name, ordinal_position'), {'schema':'public'}).all()); print(c.execute(text('SELECT c.relname, con.conname, pg_get_constraintdef(con.oid) FROM pg_constraint con JOIN pg_class c ON c.oid = con.conrelid JOIN pg_namespace n ON n.oid = c.relnamespace WHERE n.nspname = :schema ORDER BY c.relname, con.conname'), {'schema':'public'}).all()); c.close(); e.dispose()"
```

Expected: native uuid IDs/FKs, timestamp with time zone columns, JSONB delegated
permissions, defaults described above, unique email/pair, role/permission checks,
and two RESTRICT FKs. These three identity tables, four S1.2 and six S1.3 tables; no S1.4+ tables.

For persisted record verification use the targeted tests: they commit and close
the writer Session, then independently reload/assert actual stored fields and
relationships. Constraint tests execute both ORM and raw SQL writes to PostgreSQL.
No manual fixture write into the ordinary development database is necessary.

POSIX equivalents: `sh scripts/reset_db.sh`, `.venv/bin/alembic upgrade head`,

## Failure paths, reset/retry and limitations

Duplicate email/pair, invalid role/FK or reserved permissions produce PostgreSQL
integrity failures; rollback the failed Session transaction before further writes.
Reset retry/guards are in [DATABASE_RESET](../runbooks/DATABASE_RESET.md). Downgrade
to 0001_scaffold drops these three tables and their rows, so it is destructive.
No automatic soft-delete, owner-count, active-parent, timezone-catalog, email provider,
credential security or permission-engine policy is supplied by these models.
Future API contracts and auth/authorization remain PROPOSAL; S1.2/S1.3 persistence
is documented separately, S1.4+ remains future.
